# 개발 위키 기록 규칙

## 구조

```
docs/wiki/
├── Home.md                              색인: 진행 현황, 작업 로그, 문제 해결 목록
├── process.md                           개발 프로세스 설명 (절차가 바뀌면 갱신)
├── work-items/<YYYYMMDD>-<slug>/        작업 항목 하나 = 폴더 하나
│   ├── index.md                         개요 · 설계 결정 · 구현 요약 · 문제 목록 · 배운 점
│   ├── verification.md                  ②④⑦ 관문별 체크리스트 결과 (차수별)
│   └── testing.md                       ⑤ 테스트 설계 · 실행 · 결과 · 완료 조건 대조 (회차별)
└── troubleshooting/<slug>.md            문제 하나 = 한 페이지 (여러 작업에서 링크)
```

템플릿: `docs/wiki/_templates/` 의 `work-item-index.md`, `verification.md`, `testing.md`, `troubleshooting.md`. 새 페이지는 템플릿의 절 순서를 그대로 따른다.

## 골라 읽기 규칙 (처음부터 끝까지 읽지 않아도 되게)

- **모든 페이지 첫머리에 `> 요약` 3줄**을 둔다: ① 결론 ② 무엇이 바뀌었나 ③ 다음 사람이 알아야 할 것. 페이지를 여기까지만 읽어도 무엇이 있었는지 알 수 있어야 한다.
- **트러블슈팅 페이지는 요약 첫 줄이 "한 줄 해결"**이다(무엇을 하면 풀리는가). 미해결이면 "미해결 — 현재 우회 방법"을 쓴다.
- 요약 아래 상태 표, 그 아래 본문. 본문 절 이름은 템플릿 그대로 둬서 `페이지.md#절-이름` 링크가 늘 같은 곳을 가리키게 한다.
- Home.md는 **세 가지 입구**를 둔다:
  1. 작업 로그 (날짜순) — 무슨 작업이 있었나
  2. 문제 해결 (분류별 표, "이럴 때 보세요" 열 = 증상 · 에러 문구) — 지금 겪는 증상으로 찾기
  3. 주제별 색인 — "왜 이렇게 되어 있지?"에 답함. 주제 · 정해진 것 한 줄 · 근거 페이지(절 앵커까지). 설정값 · 규칙 · 도구처럼 나중에 누가 "왜?"라고 물을 만한 것을 올린다.
- 같은 사실을 여러 곳에 길게 반복하지 않는다. 한 곳에 쓰고 나머지는 링크한다.

## 검증 기록 (verification.md) 규칙

- 관문 ②④⑦마다 **차수별로** 체크리스트 전체 표를 남긴다. REVISE였던 1차를 지우고 통과한 2차만 남기지 않는다.
- 각 항목의 결과와 근거(`파일:줄` 또는 문서 절)를 run 문서에서 옮긴다. 근거가 비어 있으면 "근거 없음"이라고 쓴다.
- 지적 사항마다 "다음 차수에서 무엇을 바꿔 반영했는가"를 한 줄로 잇는다.
- 사람 확인(계획 승인)의 일시와 사용자 코멘트도 여기에 남긴다.

## 테스트 기록 (testing.md) 규칙

- **테스트 설계**: 이번에 새로 쓴 테스트마다 종류(단위 / 통합 / 정책 / 의존성 중단), 검증 의도, 대응 완료 조건, 관련 원칙.
- **실행 기록**: 환경(서비스 상태, 도구 버전), 실행한 명령, 결과 마지막 줄 원문, flaky 반복 결과, 의존성 중단 테스트 결과.
- **완료 조건 대조표**: 모든 AC가 어떤 테스트로 확인됐는지.
- 개선 사이클이 있었다면 회차마다 따로 남긴다. 실패한 회차의 출력도 지우지 않는다.
- **증거 보존:** run 폴더는 git에서 제외되므로, `.claude/runs/<run>/evidence/`를 통째로 `docs/wiki/work-items/<run>/evidence/`에 복사한다(MANIFEST.tsv 포함, 파일 내용 수정 금지). 복사 뒤 `python .claude/tools/evidence.py docs/wiki/work-items/<run> --verify`로 전부 "일치"인지 확인하고 그 출력을 testing.md에 붙인다. testing.md의 모든 결과 줄은 `evidence/NN-….log` 링크를 단다.
- 복사 전에 로그에 비밀 값(토큰, 비밀번호, 키)이 섞였는지 확인한다. 섞였으면 복사하지 않고 멈춰 오케스트레이터에게 보고한다(가려서 고치면 sha256이 달라져 증거가 깨진다).

## 무엇이 "문제 상황"인가

아래 중 하나라도 있으면 트러블슈팅 페이지를 만든다 (이미 같은 원인의 페이지가 있으면 "재발 기록" 절에 추가).

- 관문에서 REVISE · BLOCK이 나온 경우 (지적 사항이 곧 문제 상황)
- 테스트 실패 · flaky · 환경 문제 (Docker, 포트, 버전)
- 계획과 다르게 구현해야 했던 경우 (build-notes의 "계획에 없던 변경")
- 불변 원칙 위반이 발견된 경우 — **해결됐어도 반드시 기록**
- 하네스 · 도구 자체의 문제 (훅, 인코딩, 권한)

전부 APPROVE로 한 번에 통과했다면 작업 페이지의 "문제 상황" 절에 "없음"이라고 쓰고 트러블슈팅 페이지는 만들지 않는다.

## 사실만 쓴다

- 모든 문장은 근거가 있어야 한다: run 폴더 문서(`.claude/runs/...`), 명령 출력, 커밋, 코드 위치(`파일:줄`).
- run 폴더는 git에 올라가지 않으므로 **경로만 링크하지 말고 핵심 내용(오류 메시지 원문, 판정 이유)을 페이지에 옮겨 적는다.**
- 수치(지연, 차단율, 테스트 수)는 실제 출력에 있는 값만 쓴다. 추정치는 "추정"이라고 표시한다.
- 해결하지 못한 문제는 상태를 `미해결`로 두고 그대로 남긴다. 좋게 보이도록 빼거나 고쳐 쓰지 않는다 (원칙 7).

## 문체

- 한국어, 평서문. 나중에 면접에서 설명할 수 있게 "왜"를 한 줄씩 붙인다.
- 문제 해결 페이지는 **증상 → 원인 → 해결 → 검증 → 재발 방지** 순서. 원인이 여러 겹이면 "왜?"를 반복해서 근본 원인까지 적는다.
- 코드 조각은 문제를 보여주는 최소 분량만.

## Home.md 갱신

- 작업 로그 표에 한 줄 추가: 날짜 · 항목 · 결과(완료/중단) · 관문 재시도 횟수 · 링크
- 문제 해결 표: 해당 **분류 표**(환경 / 하네스 / 설계 / 구현 / 테스트)에 한 줄 추가: 문제 한 줄 · **이럴 때 보세요(증상 · 에러 문구)** · 상태 · 날짜 · 링크
- 주제별 색인: 이번 작업에서 정해진 설정값 · 규칙 · 도구가 있으면 한 줄 추가(주제 · 정해진 것 · 근거 링크). 이미 있는 주제면 그 줄을 최신으로 고치고 이전 근거도 남긴다
- 진행 현황의 해당 단계 체크를 `docs/plan.md`와 맞춘다
- 하네스 절차(단계 · 기준 · 담당)가 바뀌었으면 `process.md`도 갱신한다

## 직접 호출될 때 (/dev-wiki)

`/work-item` 밖에서 생긴 문제(환경 설정, 도구 문제 등)를 기록한다. `$ARGUMENTS`와 이 대화에서 확인된 사실만으로 트러블슈팅 페이지를 쓰고 Home.md에 추가한다. 대화에 근거가 없는 절은 "확인 필요"로 남긴다.
