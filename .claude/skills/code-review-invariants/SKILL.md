# ④ 구현 검증 체크리스트

`git diff`(새 파일은 `git status`로 확인 후 직접 읽기), `01-plan.md`, `03-build-notes.md`를 대조한다. 결과는 `04-code-review.md`.

## A. 계획 일치

| # | 항목 | 실패하면 |
|---|---|---|
| A1 | 바뀐 파일이 계획의 "바꿀 파일"과 일치한다. 추가된 파일은 build-notes에 이유가 있다 | REVISE |
| A2 | 계획의 "먼저 쓸 테스트"가 전부 작성됐다 | REVISE |
| A3 | "하지 않는다"로 적힌 일을 하지 않았다 | REVISE |

## B. 불변 원칙 (`broker-invariants` 금지 패턴 대조)

변경된 코드 경로마다 확인한다. 위반은 `파일:줄`과 원칙 번호로 적는다.

| # | 확인 방법 |
|---|---|
| B1 | 모든 `except` · 기본값 · 분기에서 기본 결과가 `deny`인가. `!= "deny"` 형태의 허용 판정이 없는가 |
| B2 | 외부 호출에 타임아웃이 있는가 |
| B3 | 응답 · 로그 · 오류 메시지에 자격 증명이 새지 않는가 |
| B4 | 확인과 차감이 분리된 곳이 없는가 (조회 후 조건문 후 쓰기) |
| B5 | 판단 저장과 outbox가 같은 트랜잭션인가. 거부 경로도 기록되는가 |
| B6 | 캐시가 위임 버전 없이 TTL에만 의존하지 않는가 |
| B7 | 테스트가 결과와 이유를 둘 다 assert하는가. 도구 미호출을 확인하는가 |

## C. 기본 정확성

| # | 항목 |
|---|---|
| C1 | 비동기 코드에서 await 누락, 공유 상태 경쟁 |
| C2 | 비밀 값이 코드 · 테스트 · `env.example` 값에 하드코딩되지 않음 |

## 판정

- B 항목 위반이 하나라도 있으면 최소 REVISE
- 위반을 "개발 편의" · "나중에 고침"으로 정당화하는 주석 · 플래그가 있으면 BLOCK
