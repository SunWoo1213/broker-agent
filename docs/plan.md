# 진행 계획

기간은 정하지 않고 단계 순서만 정한다. 1단계만 끝나도 "브로커를 거쳐야만 도구를 쓸 수 있는 에이전트"로 설명할 수 있는 결과물이 남도록 순서를 잡았다.

| 단계 | 목표 | 결과물 |
|---|---|---|
| 1 | 게이트웨이 ①②③⑦ + 모의 도구 + 데모 에이전트 | 브로커를 거치지 않으면 도구를 호출할 수 없는 최소 형태 |
| 2 | 승인(⑤), 임시 토큰(⑥) | 인자 해시에 묶인 승인, 서명 토큰 |
| 3 | 누적 한도(④), 동시성 테스트, 공격 시나리오 평가 1차 | 시나리오별 차단율 첫 측정 |
| 4 | 감사 로그(⑧), 취소 전파 | 위변조 탐지 체인, 취소 반영 시간 |
| 5 | AWS · Terraform, 배포 자동화, 모니터링, 부하 테스트 | 브로커가 더하는 p95 지연, 초당 처리량 |
| 6 | 수치 정리, README, 시연 영상 | 브로커 없음 vs 있음 비교표 |

## 2단계 — 승인(⑤) · 임시 토큰(⑥)

> 시작 전 `decisions.md`에 적을 결정: **D10** 인자 해시 계산 규칙(정규화 JSON: 키 정렬 · 공백 제거 · 숫자 표기 통일 → SHA-256), **D11** 토큰 서명 방식(KMS 비대칭 키 ES256 + JWKS, `jti` 1회용), 열린 질문 "승인 후 재개 방식"을 **승인 ID로 재호출**로 확정.

### 7. 데이터 모델 (2차)
- [ ] `approvals` 테이블: 위임, 작업, 인자 원문, 인자 해시, 상태, 만료 시각, 승인자
- [ ] 상태 전환(대기 → 승인 / 거절 / 만료, 승인 → 실행됨 / 만료)을 DB 제약 조건과 코드 양쪽에서 강제. 그림에 없는 전환은 실패

### 8. 승인 흐름
- [ ] 정책이 "승인 필요"를 주면 승인 요청을 만들고 에이전트에 `승인 대기(id)` 반환
- [ ] 관리 API: 승인 · 거절 엔드포인트. **승인자는 그 위임을 준 사용자 본인만** 가능
- [ ] 에이전트가 승인 ID로 재호출하면 인자 해시를 다시 계산해 대조. 한 글자라도 다르면 거부 (D3)
- [ ] 승인은 한 번만 실행된다 (실행됨 상태에서 재사용 시 거부)
- [ ] 만료 처리: 기한이 지난 대기 · 승인 건을 만료로 바꿈 (로컬은 주기 작업, AWS는 EventBridge Scheduler)
- [ ] 정책: 위험도 높음 → "승인 필요" 활성화 (1단계의 임시 거부 규칙 교체)

### 9. 승인 화면 (최소)
- [ ] Keycloak을 Compose에 추가, 직원 2명 계정 · OIDC 로그인
- [ ] 내 승인 대기 목록 + 인자 원문 표시 + 승인 / 거절 버튼. 이것 외의 UI는 만들지 않음

### 10. 임시 토큰
- [ ] 토큰 내용: 도구, 작업, 인자 해시, 위임 ID, `jti`, 만료 5분 (D4)
- [ ] 로컬은 LocalStack KMS로 서명, 게이트웨이가 JWKS 제공
- [ ] 모의 도구 3종이 토큰만 받도록 교체 (1단계의 공유 비밀 헤더 제거): 서명 · 만료 · 도구/작업 일치 · **받은 인자로 다시 계산한 해시 일치** · `jti` 재사용 차단
- [ ] KMS 서명 실패 · JWKS 조회 실패 = 거부

### 11. 응답 필터 (⑦ 후반)
- [ ] `customer.lookup` 응답의 전화번호 · 계좌번호를 가림. 가릴 필드 목록은 도구 작업 설정(데이터)으로 관리
- [ ] 필터 적용 중 오류 = 응답을 돌려주지 않음 (원문 유출 대신 거부)

### 12. 데모 에이전트 (승인 대기)
- [ ] LangGraph `interrupt`로 승인 대기 시 멈추고, 승인 후 같은 인자로 재호출해 재개
- [ ] "18만 원 청구 → 승인 → 실행" 시연

### 13. 2단계 완료 판정
- [ ] 승인 뒤 금액을 바꿔 재호출하면 거부된다 (테스트)
- [ ] 거절 · 만료 · 이미 실행된 승인으로 재호출하면 거부된다 (테스트)
- [ ] 다른 사용자가 승인하려 하면 실패한다 (테스트)
- [ ] 도구는 토큰 없음 · 만료 · 다른 작업용 · 인자 변조 · 재사용 토큰을 모두 거부한다 (테스트)
- [ ] KMS를 멈추면 모든 요청이 거부된다 (테스트)
- [ ] 고객 조회 응답에 민감 필드 원문이 없다 (테스트)

## 3단계 — 누적 한도(④) · 동시성 · 평가 1차

> 시작 전 결정: **D12** 한도의 기준 저장소와 복구 방식(Redis는 빠른 예약용, `quota_ledger`가 원본. Redis 재시작 시 ledger로 다시 채움), **D13** OPA와 한도의 역할 분담(OPA는 "일일 한도 초과 시 승인 필요" 같은 판단, 실제 차감은 Redis Lua만).

### 14. 한도 예약 → 확정 / 해제
- [ ] `quota_ledger` 테이블 (위임별 · 기간별 예약액 / 확정액)
- [ ] Redis Lua 스크립트 3개: 예약(확인 + 차감 한 번에), 확정, 해제. 요청 ID로 멱등 처리 (D2)
- [ ] 해제 시점: 도구 호출 실패, 승인 거절 · 만료, 예약 후 일정 시간 확정 없음(회수 작업)
- [ ] ledger와 Redis 주기 대조 + 불일치 알림
- [ ] Redis 연결 실패 = 거부. "잔여 한도 조회 후 실행" 형태의 코드가 없는지 리뷰 항목에 포함

### 15. 동시성 테스트
- [ ] 한도 직전에서 요청 20개 동시 → 초과 0건 (D2 검증)
- [ ] 게이트웨이 프로세스 2개 이상에서도 동일
- [ ] 한도 쪼개기(10만 원 × 5회)가 일일 한도에서 걸림

### 16. 공격 시나리오 평가 1차
- [ ] **실행 전에** 시나리오 6종과 채점 기준을 `eval/`에 고정하고 커밋 (원칙 7: 결과를 보고 바꾸지 않음)
- [ ] 정상 작업 세트(오차단율 측정용)도 함께 고정
- [ ] 비교 대상: 브로커 없음(에이전트가 도구 키를 직접 가짐) vs 있음, 같은 모델 · 같은 프롬프트
- [ ] LLM이 끼는 시나리오(프롬프트 주입)는 모델 · temperature 고정, N회 반복해 비율로 기록
- [ ] 결과 리포트 `eval/reports/`: 시나리오별 차단율, 오차단율, **막지 못한 시나리오와 원인**
- [ ] 이후 ⑤ 테스트 단계에 `eval-runner` 합류

### 17. 3단계 완료 판정
- [ ] 동시 요청 20개에서 한도 초과 0건 (테스트)
- [ ] 도구 호출 실패 · 승인 거절 · 만료 시 예약이 해제된다 (테스트)
- [ ] Redis를 멈추면 모든 요청이 거부되고, 재시작 후 ledger 기준으로 복구된다 (테스트)
- [ ] 평가 1차 리포트가 있고 재실행하면 같은 절차로 다시 나온다

## 4단계 — 감사 로그(⑧) · 취소 전파

### 18. 감사 로그
- [ ] `outbox` 테이블: 판단 결과와 같은 트랜잭션으로 기록 (DB에 못 쓰면 판단 자체가 거부) (원칙 5)
- [ ] 감사 워커: outbox → `audit_events` (순번, 이전 해시, 현재 해시). 워커 1개 직렬 처리, outbox ID로 중복 기록 방지
- [ ] 체인 끝값을 S3(LocalStack, 객체 잠금)에 주기 보관
- [ ] 체인 검증 CLI: 수정 · 삭제 · 순서 바꿈을 찾아 위치를 보고
- [ ] 1단계의 임시 판단 로그를 감사 이벤트로 교체

### 19. 취소 전파
- [ ] 게이트웨이 위임 캐시 + 위임 버전 번호 (D6)
- [ ] 관리 API 취소 → PostgreSQL 버전 증가 + Redis Pub/Sub 알림 → 모든 게이트웨이 캐시 무효화
- [ ] Pub/Sub 메시지 유실 대비: 요청마다 Redis의 위임 버전 키와 캐시 버전을 대조. Redis 불가 = 거부
- [ ] 취소 → 차단까지 걸린 시간 측정 (p50 / p99), 결과를 기록
- [ ] 취소 시 대기 중 승인 · 미확정 예약도 정리

### 20. 관리 API · 관리자 화면 (최소)
- [ ] 에이전트 · 도구 등록, 에이전트 정지, 위임 생성 · 취소
- [ ] 감사 로그 조회 (필터: 사용자 · 에이전트 · 판단 결과)
- [ ] 관리자 권한은 Keycloak 역할로 확인

### 21. 4단계 완료 판정
- [ ] 워커를 처리 중 강제 종료해도 이벤트 유실 0건 · 중복 0건 (테스트)
- [ ] DB의 감사 행 하나를 고치면 검증 CLI가 찾아낸다 (테스트)
- [ ] 취소 직후 요청이 거부되고, 반영 시간 수치가 있다 (테스트 + 측정)
- [ ] 평가 시나리오 "만료 · 취소 권한 재사용" 재실행 결과 기록

## 5단계 — AWS 배포 · 모니터링 · 부하 테스트

> Claude는 `terraform plan`까지만 한다. `apply` / `destroy`는 사용자가 직접 실행하고, 측정 · 시연이 끝나면 바로 `destroy`한다.
> 시작 전 결정: **D14** NAT Gateway 대신 VPC 엔드포인트(S3 · ECR · KMS · Secrets Manager · Logs)로 비용을 줄일지.

### 22. Terraform
- [ ] 원격 상태(S3 + 잠금), 모듈 `network` · `data` · `compute` · `security`
- [ ] `security`: KMS 서명 키, Secrets Manager, 서비스별 최소 권한 IAM 역할
- [ ] `compute`: ECS 서비스 `mcp-gateway`(+ `opa` 사이드카, 자동 확장) · `control-api` · `audit-worker` · `keycloak` · 모의 도구 3종, ALB
- [ ] 도구 서비스는 게이트웨이 보안 그룹에서만 접근 가능

### 23. 배포 자동화
- [ ] GitHub Actions: 테스트 → `opa test` → 이미지 빌드 → ECR → ECS 배포 (OIDC 인증, 장기 키 없음)
- [ ] Alembic 마이그레이션을 배포 단계에 포함
- [ ] OPA 정책 묶음을 S3에서 받아오고 `policy_versions`에 기록 (D5)

### 24. 모니터링
- [ ] CloudWatch 지표: 판단별 건수, 거부율, 게이트웨이 지연, outbox 지연, 취소 반영 시간
- [ ] 경보: 거부율 급증, outbox 적체, 한도 대조 불일치
- [ ] 로그에 인자 원문 · 토큰이 남지 않는지 확인

### 25. 부하 테스트
- [ ] k6: 도구 직접 호출 vs 브로커 경유 → **브로커가 더하는 p95 지연**, 초당 처리량
- [ ] 목표 p95 20ms 초과 시: 구간별 원인 분석 후 D8(Python)과 열린 질문(OPA vs Cedar) 재검토

### 26. AWS에서 fail-closed 재확인
- [ ] OPA 사이드카 · ElastiCache · RDS에 닿지 않게 만든 상태에서 요청이 모두 거부되는지 확인

### 27. 5단계 완료 판정
- [ ] `terraform apply` 한 번으로 전체 환경이 뜨고, 데모 시나리오가 AWS에서 끝까지 돈다
- [ ] 부하 테스트 수치(p95 지연, 초당 처리량)가 기록되어 있다
- [ ] `destroy` 후 과금 리소스가 남지 않음을 확인
